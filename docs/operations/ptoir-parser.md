# `/ptoir-parser` — ПТОиР

Design decisions behind this page's operations. Moved from CLAUDE.md; keep them up to date when changing the operation.

## Изменение моточасов

"Изменение моточасов" on `/ptoir-parser` (`validate_change_hours_rows`, `sql_builders/ptoir.change_hours`) overwrites `counter_active.value` of the ПТОиР's asset (`id_active = ptoir.id_active AND id_counter_type = 1`; `ptoir` itself has no `value` column) with the file's `значение` × 10 — the file holds hours with at most one decimal, the column holds integer tenths. The updates run under `SET session_replication_role = replica`, because `counter_active_hours_jump` (PL/Python, BEFORE UPDATE) takes a written `value` as a source reading and **adds** it to the old total instead of replacing it. Both `SET`s and the updates share one transaction: a plain `SET` is rolled back with it, so a failed run cannot return the pgbouncer connection to the pool with every trigger (FKs included) still off. `value_source` and `date` are deliberately left alone — a user decision; the next regular reading is therefore still counted from the old `value_source`. The overwrite is irreversible, so `log/ptoir_hours_<timestamp>.log` records each asset's old `value`/`value_source`.

## Удалить ПТОиР

"Удалить ПТОиР" on `/ptoir-parser` (`validate_delete_rows`, `sql_builders/ptoir.delete`, issue #19) deletes ПТОиР by `ptoir.number_ptoir` from the "ПТОиР" column (first sheet of "Удалить ПТОиР и БПТОиР.xlsx"; БПТОиР / `main_ptoir` is out of scope). Unlike every other operation a row error does **not** block the file: a missing number or empty cell is reported and skipped, the rest runs, and only "no ПТОиР found at all" fails (user decision). Per ПТОиР: all its orders get `id_ptoir = NULL` (kept, never deleted — including orders without an asset), then `ptoir_level_warning`, `ptoir` and **every** `ptoir_status` row with the same `number_ptoir` (the status history, linked by text only) are deleted — in that order, because `ptoir.id_ptoir_status` references `ptoir_status`. Lookups are bulk (files run to ~6k rows); the log `log/delete_ptoir_<timestamp>.log` lists the detached `order_number`s, but no snapshot of the deleted rows is kept (user decision).

## Удалить БПТОиР

"Удалить БПТОиР" on `/ptoir-parser` (`controllers/ptoir_parser/delete_main.py`, `sql_builders/ptoir.delete_main`, issue #21) deletes main maintenance records (`main_ptoir`) by `number_ptoir` from the `БПТОиР` column (sheet "Удалить БПТОиР"), partially like "Удалить ПТОиР". Every `ptoir` of a deleted БПТОиР goes through `ptoir.delete()` itself — the same statements as #19, so the two cannot drift; `load_ptoirs` / `match_rows` in the package's `common.py` give both validators the same ПТОиР rows. Then the БПТОиР's rows in `actives_to_main_ptoir`, `design_number_to_main_ptoir`, `main_ptoir_trigger`; then, one statement per link table, `main_ptoir_to_config_counter` / `main_ptoir_to_techcard_interval` in a CTE whose outer `DELETE` removes the `main_ptoir_config` / `techcard_interval` rows they pointed at (1:1 on the copy, orphaned otherwise) — a CTE and its outer statement share one snapshot, so the `NOT EXISTS` guard tells another БПТОиР's link apart by `id_main_ptoir NOT IN (…)` rather than by the link being gone, and the FK is checked at the end of the statement. Last `main_ptoir` and every `main_ptoir_status` row with its number (the history; `main_ptoir.id_main_ptoir_status` points at it). Assets, design numbers and techcards are never touched.
