# `/parser` — models and assets from models

Design decisions behind this page's operations. Moved from CLAUDE.md; keep them up to date when changing the operation.

## Изменить okz в модели / Добавить строку в модель: creating missing car places

"Изменить okz в модели" and "Добавить строку в модель" **create** a car place the file names but `car_place` lacks, instead of reporting "car_place не найден" (`sql_builders/car_place.py`, issue #8). A validated row refers to its car place by id (`int`, it exists) or by name (`str`, it has to be created). `insert_missing()` emits one `INSERT … (name, car_number) … ON CONFLICT (name) DO NOTHING RETURNING name` per name, before the model statements; `car_number` comes from the `_(NN)` suffix via `parse_car_number()` (shared with `train_parser`), every other column is left to its default. The model statements reference a new car place through `(SELECT id … WHERE name = …)`: its id is unknown when the file is generated, and `ON CONFLICT` keeps the file runnable if someone creates the name before it runs. Both execute paths run the builder's own lines through `controllers/parser/common.execute_sql_lines()`, which collects the `RETURNING` rows — so the message and log list only the names that run actually created — and uses `exec_driver_sql`, not `text()`: a typed name is inlined into the SQL, and `text()` reads a `:1` after a space or bracket as a bind parameter. "Изменить okz в активе по модели" still reports a missing car place as an error.

## Изменить ТМЦ в модели

"Изменить ТМЦ в модели" (`controllers/parser/change_design_number.py`, `sql_builders/models.change_model_design_number`, issue #17) sets `models.id_design_number` from `id` + `new_itemnum` (exact `design_number.number`, never created); an optional `itemnum` is checked against the model's **current** number, because exports go stale (the example's `lsn` already was). The two unique indexes containing `id_design_number` — `(id_car_place, id_train_type, id_design_number) WHERE is_default` and the five-column `models_id_many_field_key` — are checked up front against the DB and between file rows; a NULL part never collides there, so such keys are skipped. A conflicting DB model is checked in its current state, which rejects swaps **and chains** (B taking the number A gives up in the same file) — no two-phase update, unlike okz. `actives.id_design_number` is left alone.

## Изменить ТМЦ в активе по модели

"Изменить ТМЦ в активе по модели" (`controllers/parser/change_design_number_active.py`, `sql_builders/models.change_design_number_active`, issue #18) sets `actives.id_design_number` for the assets built from a model, from the same `id` / `itemnum` / `new_itemnum` sheet as "Изменить ТМЦ в модели". Unlike "Изменить okz в активе по модели" it ignores the file's `lsn` and takes the positions from the model's **current** `lcn` in the DB (8 of the 12 example `lsn`s were stale and would have hit other positions), fanned out over every train of the type; only assets still carrying `itemnum` change, and `itemnum` is never compared with the model's own number, so the two buttons run in either order. A repeat is keyed by (model, old number) — one model may carry several old numbers — and a chain on one position (X→Y in one row, Y→Z in another) is rejected: it runs right once, but re-running the downloaded file would carry the X assets on to Z. `counter_active` and `id_unit_type` are left alone (`actives_trgger` builds counters on INSERT only) — the success message points to "Синхронизация counter_active". The affected assets are selected (`design_number_active_targets`) and logged before the UPDATE. `column_key` / `row_text` / `parse_model_id` in `controllers/parser/common.py` are shared with #17.
