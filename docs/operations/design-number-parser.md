# `/design-number-parser` — design numbers (ТМЦ)

Design decisions behind this page's operations. Moved from CLAUDE.md; keep them up to date when changing the operation.

## Изменить ТМЦ номер

"Изменить ТМЦ номер" on `/design-number-parser` (`validate_rename_rows`, `sql_builders/design_number.rename`, issue #14) renames `design_number.number` from the `Старый ТМЦ` / `Новый ТМЦ` columns. Its purpose is fixing invisible defects (trailing spaces, `\xa0`, Cyrillic look-alikes), so — unlike the page's other operations — the old number is matched **exactly, never stripped**, and a new number with edge whitespace or `\xa0` is rejected rather than cleaned; messages quote numbers via `repr()` so those characters are visible. Chains/swaps need no check of their own: every old number must exist in the DB, so a new number equal to another row's old one already fails "уже существует". Renaming is safe because every FK into `design_number` references `id`.

## Обновить ТМЦ номер

"Обновить ТМЦ номер" on `/design-number-parser` (`validate_update_rows`, `sql_builders/design_number.update_full`, issue #15) is a **full overwrite** of 14 columns and the `maint_use` links of existing design numbers (never an insert) from the 16-column export (`dn_upd.xlsx`); `NULL`/empty means SQL NULL, not "leave unchanged". The file's `maint_use` (comma list) is the complete link set: missing links are inserted, others deleted. Reference names match trimmed and case-insensitively, and a name occurring twice in its catalogue is an error, never the first match — except `measure_type`, which really has duplicates (`'пог. м'` 13/22, `'рул'` 15/21): there the row with a non-null `code_1c` wins, and the highest id breaks any remaining tie (user decision). Files run to ~13k rows, so validation bulk-loads every catalogue and the file's numbers once, and execution sends all statements as one batch over the raw asyncpg connection. The rollback is `update_full()` applied to `snapshot_design_numbers()` of the old state — the same builder, so it restores exactly — and is written to `log/update_design_number_<timestamp>.log` **before** the run. Schema defect, documented not fixed: FK `id_maint_use_use_to_maint_use_fk` points `design_number_to_maint_use.id_maint_use` at `design_number(id)` instead of `maint_use(id)`; it only holds because design numbers with ids 1–11 exist — `id_maint_use` is a `maint_use` id.

## Создать ТМЦ номер

"Создать ТМЦ номер" on `/design-number-parser` (`validate_create_rows`, `sql_builders/design_number.create` / `delete_created`, issue #16) **creates** design numbers from the same 16-column sheet and **fully updates** (as "Обновить ТМЦ номер") the ones that already exist — a user decision after #16 shipped insert-only; `sql_builders/design_number.create_or_update` splits rows by `DesignNumberRow.id` (`None` = new) and `undo_create_or_update` is the rollback (DELETE the created, `update_full` of the snapshot for the updated); `_parse_fields()` holds every field rule and is shared with "Обновить ТМЦ номер", the two validators differ only in the number check (`DesignNumberRow.id` is `None` for a row being created). A number is rejected if it is *similar* — equal after `strip()` and `casefold()` — to an existing number or to another row of the file: a dirty `'X '` in the DB must be fixed with "Изменить ТМЦ номер" rather than shadowed by a near-duplicate `'X'`. Inserts are plain (no `ON CONFLICT`), so a number created meanwhile fails the whole transaction; the rollback is logged before the run. DB defect, documented not fixed: the only INSERT trigger on `design_number` (`tr_design_humber_to_wheelset_to_design_number`) is `FOR EACH STATEMENT` but reads `NEW`, which is NULL there — so it never adds the `skripka.wheelset_to_design_number` row it means to for `unit_type` 3 "Колесная пара" (51 of 63 wheelset numbers have one); this operation does not write to `skripka`.
