# `/techcard-parser` — techcards

Design decisions behind this page's operations. Moved from CLAUDE.md; keep them up to date when changing the operation.

## Создать техкарты / Наполнить операциями

"Техкарты" (`/techcard-parser`, issue #12) creates techcards from the "Создать техкарты" sheet (`validate_techcard_rows`, `sql_builders/techcards.create`). Every column that is not one of the sheet's known columns is a classifier — by name, never by position: the page posts its rows through Jinja's `tojson`, which **sorts the keys**, so "the columns after 'Классификация техкарты'" is meaningless on the server. Classifiers are matched by header against `classifier.name` within the row's `classifier_type`; a cell becomes a `techcard_to_specification` row via `specification.description` (`is_delete` respected, `is_active` ignored — `И5`/`И7`/`И8` are inactive). The techcard and its `techcard_status` point at each other (`techcard.id_techcard_status`, `techcard_status.techcard_number`), so each statement takes **both ids from the sequences up front** in a CTE and inserts the status before the techcard: a sibling CTE cannot see a row another one inserted, so "insert, then UPDATE with the status id" does nothing; the FKs are checked at the end of the statement. An empty "Статус" is allowed: the techcard gets `id_techcard_status = NULL` and no `techcard_status` row is created. An empty "Классификация техкарты" is allowed too (`id_classifier_type = NULL`, as on most existing techcards) — but then no classifier cell may be filled, since classifiers are only looked up within the row's type. `id_users` is NULL on both rows (user decision; it used to be a hardcoded 505); `date_status` is `now() AT TIME ZONE 'Europe/Moscow'` (the DB runs in UTC). The second operation, "Наполнить операциями" (issue #13, `validate_operation_rows`, `sql_builders/techcards.add_operations`), fills `techcard_work_operation` from the "Наполнить техкарты операциями" sheet and requires the techcards to exist already — sheet 1 is executed first. A row naming only the techcard is a techcard without operations and is skipped; "Описание вложенной техкарты" is not stored, only checked against the nested techcard's `description`. The page is a package like `controllers/parser/` (`page.py`, `create.py`, `operations.py`, `common.py`); both operations run through `sql_tasks`.
